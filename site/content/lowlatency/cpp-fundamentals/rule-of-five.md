# Rule of Five

> **Why a quant dev must own this:** the special member functions decide whether
> your type *copies*, *moves*, or *leaks*. Get one wrong on a type that owns a
> raw resource and you ship a double-free or a silent O(n) copy where you wanted
> an O(1) move; forget `noexcept` on the move and `std::vector` quietly copies on
> every reallocation. The Rule of Five (and its better half, the Rule of Zero)
> is the contract for correct, fast value types — and "what are the five special
> members and when must you write them?" is a guaranteed interview question.

## First principles: the special member functions

The compiler can generate up to **six** special members for a class. Five of
them concern copying, moving, and destruction — the "Rule of Five" set:

```cpp
// C++17
struct T {
    ~T();                        // 1. destructor
    T(const T&);                 // 2. copy constructor
    T& operator=(const T&);      // 3. copy assignment
    T(T&&) noexcept;             // 4. move constructor
    T& operator=(T&&) noexcept;  // 5. move assignment
};
// (the sixth special member is the default constructor T(), not part of the rule)
```

**The Rule of Five:** *if you write (or `=delete`) any one of these five, you
almost certainly need to consider all five.* The reason: you only hand-write
them when your class manages a resource by hand (a raw `new`/`malloc`, an OS
handle, a lock). The moment one is non-trivial, the compiler's defaults for the
others are wrong — they'll do member-wise copies of a pointer you meant to deep-
copy or transfer.

> **History:** this was the *Rule of Three* (dtor, copy ctor, copy assign)
> before C++11. Move semantics added the two move members, making it five.

## Why writing one suppresses others (the generation rules)

The defaults aren't independent — declaring some members *suppresses* the
implicit generation of others. The rules you must memorize:

```text
If you declare...            then the compiler...
  a destructor               does NOT generate move ops (and copy ops are deprecated)
  a copy ctor or copy assign does NOT generate move ops; the other copy op deprecated
  a move ctor or move assign does NOT generate either copy op (they're deleted)
```

```text
                 generated by default?
                 dtor  copy-ctor  copy-asn  move-ctor  move-asn
  declare none    yes     yes       yes        yes        yes
  declare dtor    --      yes(dep)  yes(dep)   NO         NO      <- silent: no moves!
  declare copy    yes     ...       ...        NO         NO
  declare move    yes     DELETED   DELETED    ...        ...
```

The dangerous row is the second: **the instant you write a destructor, the move
operations vanish.** Your type still *compiles* and still *works* — it just
silently *copies* everywhere you expected a move, because copy is the fallback
when no move exists. This is the most common way a "move-enabled" type secretly
isn't.

## A correct Rule-of-Five type (raw resource)

When you genuinely own a raw resource, write all five explicitly:

```cpp
// C++17 — owns a raw heap buffer; the textbook Rule of Five
#include <cstddef>
#include <utility>
#include <algorithm>

class Buffer {
    std::byte* data_ = nullptr;
    std::size_t size_ = 0;
public:
    explicit Buffer(std::size_t n) : data_(new std::byte[n]), size_(n) {}

    ~Buffer() { delete[] data_; }                                  // 1

    Buffer(const Buffer& o) : data_(new std::byte[o.size_]), size_(o.size_) {
        std::copy(o.data_, o.data_ + o.size_, data_);              // 2 deep copy
    }
    Buffer& operator=(const Buffer& o) {                           // 3 copy-and-swap
        Buffer tmp(o);                 // strong exception guarantee + self-assign safe
        swap(*this, tmp);
        return *this;
    }

    Buffer(Buffer&& o) noexcept                                    // 4 steal + null-out
        : data_(std::exchange(o.data_, nullptr)),
          size_(std::exchange(o.size_, 0)) {}
    Buffer& operator=(Buffer&& o) noexcept {                       // 5
        Buffer tmp(std::move(o));      // release ours, take theirs
        swap(*this, tmp);
        return *this;
    }

    friend void swap(Buffer& a, Buffer& b) noexcept {
        using std::swap;
        swap(a.data_, b.data_);
        swap(a.size_, b.size_);
    }
};
```

Note the two big idioms: **copy-and-swap** for assignment (one body gives you
self-assignment safety and the strong exception guarantee), and **`noexcept`
moves that null out the source** so the moved-from object's destructor is a safe
no-op.

## The Rule of Zero — what you should reach for first

The best Rule-of-Five implementation is **the one you don't write.** If every
member is itself a well-behaved RAII type (`std::vector`, `std::string`,
`unique_ptr`, `shared_ptr`), the compiler-generated special members are already
correct — they copy/move/destroy member-wise, and each member does the right
thing. So you declare *none* of the five:

```cpp
// C++17 — Rule of Zero: owns nothing raw, so write nothing special
class Order {
    std::string              symbol_;   // each member manages itself
    std::vector<Fill>        fills_;
    std::unique_ptr<Extras>  extras_;
public:
    // No dtor, no copy/move declared. Compiler generates correct ones:
    //   - destroyed member-wise
    //   - moved member-wise (vector/string/unique_ptr all move cheaply)
    //   - copied member-wise (unique_ptr is non-copyable -> Order is move-only, automatically)
};
```

> **The senior default:** *prefer the Rule of Zero. Reach for the Rule of Five
> only at the one place that touches a raw resource — and then keep that class as
> small as possible* (a thin RAII wrapper), so everything composing it stays
> Rule-of-Zero.

## `=default` and `=delete`

You don't have to choose between "write all five by hand" and "write none":

- **`=default`** asks the compiler for its implementation *explicitly* — useful
  to bring back a member the rules suppressed, or to document intent.
- **`=delete`** removes a member so using it is a compile error — the way to
  express "this type is not copyable" or "this type is move-only".

```cpp
// C++17
struct Widget {
    Widget(Widget&&)            = default;   // explicitly take the default move
    Widget& operator=(Widget&&) = default;
    ~Widget()                   = default;   // re-enable defaults the dtor would suppress
    Widget(const Widget&)       = delete;    // forbid copy: this type is move-only
    Widget& operator=(const Widget&) = delete;
};
```

> **Subtlety:** a `=default`ed special member can still end up *deleted* if a
> member/base can't support it (e.g. defaulting the copy ctor of a class holding
> a `unique_ptr`). And the move members are only generated as `noexcept` if the
> member moves are themselves `noexcept` — watch this for container performance.

## Move-only types

A *move-only* type can be moved but not copied — the natural model for unique
ownership (file handles, sockets, `unique_ptr`, `std::thread`,
`std::future`). You express it by deleting the copies and defaulting (or
writing) the moves:

```cpp
// C++17
class UniqueHandle {
    int fd_ = -1;
public:
    explicit UniqueHandle(int fd) : fd_(fd) {}
    ~UniqueHandle() { if (fd_ != -1) ::close(fd_); }

    UniqueHandle(const UniqueHandle&)            = delete;   // no copying a handle
    UniqueHandle& operator=(const UniqueHandle&) = delete;

    UniqueHandle(UniqueHandle&& o) noexcept : fd_(std::exchange(o.fd_, -1)) {}
    UniqueHandle& operator=(UniqueHandle&& o) noexcept {
        if (this != &o) { if (fd_ != -1) ::close(fd_); fd_ = std::exchange(o.fd_, -1); }
        return *this;
    }
};
```

Move-only is *the* shape for resources that must have exactly one owner — copying
them would mean two owners closing the same fd (a double-free of the resource).

## Performance & hardware reality

- **Member-wise moves are O(1) per owning member** (pointer steals), versus
  copies that are O(n) deep copies plus allocations. The whole point of getting
  the move members right is to keep the cheap path.
- **`noexcept` is load-bearing.** `std::vector` (and other containers) only
  *move* elements during reallocation if the element's move constructor is
  `noexcept`; otherwise they *copy*, to preserve the strong exception guarantee.
  A non-`noexcept` (or accidentally-suppressed) move turns vector growth into a
  copy-fest — a stealthy latency regression.
- **Accidental copies are a top HFT bug.** A type that *looks* movable but isn't
  (because a destructor suppressed the moves) will deep-copy on every `return`,
  `push_back`, and `std::move` — exactly the operations you put in hot loops.
- Rule-of-Zero types cost nothing extra: the generated specials inline to the
  same code you'd write, with the right `noexcept` deduced from the members.

```text
Cost of getting it wrong
  destructor written, moves suppressed ... every "move" is a deep copy   (correctness-cost)
  move not noexcept ...................... vector realloc copies instead  (perf-cost)
  copy not deleted on a handle type ...... double-close / double-free     (UB)
```

## Quant/HFT relevance & interview gotchas

- **Name the five:** destructor, copy ctor, copy assign, move ctor, move assign.
  (Default ctor is special but *not* part of the rule.)
- **Writing a destructor suppresses the move operations** — the single most
  important gotcha. The type then silently copies. `=default` the moves to bring
  them back, or better, don't write the destructor (Rule of Zero).
- **Declaring a move op deletes both copy ops.**
- **Prefer the Rule of Zero;** isolate raw resource management in a tiny RAII
  wrapper and let everything else compose cleanly.
- **`noexcept` on moves or `std::vector` copies on growth** — say this; it's a
  favorite follow-up.
- **Move-only = delete copies + provide moves**, the right model for unique
  ownership; copying a handle means a double-free.
- **copy-and-swap** gives self-assignment safety and the strong exception
  guarantee in one body — good to be able to write on a whiteboard.
- A `=default`ed special member can still be implicitly *deleted* if a base/member
  doesn't support it.

## Key takeaways

1. The five special members are **destructor, copy ctor, copy assign, move ctor,
   move assign**; if you write one for a resource-owning type, consider all five.
2. **Writing a destructor suppresses the implicit move operations**, so the type
   silently *copies* — the classic trap.
3. **Prefer the Rule of Zero:** compose RAII members and declare none of the
   five; the generated ones are correct.
4. Use **`=default`** to bring back/document a member and **`=delete`** to forbid
   one (e.g. to make a type move-only).
5. **Move-only types** delete the copies and provide `noexcept` moves — the model
   for unique ownership; copying a handle double-frees.
6. **Mark moves `noexcept`** or containers copy on reallocation; `noexcept` is a
   performance contract, not decoration.

## Self-check

1. List the five special members. Which sixth special member is *not* part of
   the rule?
2. You add a destructor to a class to log on teardown. What silently happens to
   its move operations, and what's the runtime consequence?
3. Why does declaring a move constructor delete the copy constructor?
4. Write the copy-assignment operator using copy-and-swap and explain the two
   guarantees it buys you.
5. How do you make a type move-only, and why is that the right model for an OS
   handle?
6. Your move constructor isn't `noexcept`. What does `std::vector` do on
   reallocation, and why?
